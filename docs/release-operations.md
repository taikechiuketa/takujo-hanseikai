# 公開と障害対応

## 公開の前提

1. `npm ci && npm test` と依存監査を通す。GitHub ActionsのProduct checksが成功していることを確認する。
2. SQLの変更は既存DBの設定と差分を確認し、復元可能なバックアップがあることを確認してから適用する。DB関数・RLSの本番反映と画面の公開は別の作業。
3. 募集APIの後方互換版を先に公開して正常性を確認し、新しい画面を公開する。
4. 変更前のコミット・新しいコミット・DBマイグレーション・デプロイID・試験結果を記録する。
5. 管理者と入力メンバーの別アカウントで、招待・保存・解除・非公開成績の匿名確認を実施する。

GitHub Pagesの既定デプロイとProduct checksは別のワークフロー。必須ステータスチェック／ブランチ保護やPagesの公開方式は運営者が設定を確認する必要がある。CIファイルの追加だけでPagesの公開がテスト成功後に限定されたとは扱わない。

## 最終確認が必要なもの

- Android ChromeとiPhone Safari/ホーム画面アプリでインストール、グループ名、起動先、アプリを閉じた状態の通知、タップ遷移。
- 新規登録と確認メール、招待の期限切れ・同時参加、二人の同時保存。
- 本番Supabaseと通知API用D1のバックアップ保存先・保持期間・復元権限・直近成功日時。別の検証環境へ復元し、件数・最新日・成績・権限・共有範囲を照合する。未確認の間は「復元可能」と判定しない。
- 運営者の問い合わせ先、通知失敗・保存失敗の検知方法、削除・退会・保持期間の手順。存在しない連絡先や監視設定を案内しない。

## 障害の切り分け

| 症状 | 確認・初動 |
| --- | --- |
| 保存失敗 | 画面を閉じる前に復旧コピー／JSONを書き出す。エラー文・発生時刻・グループ・操作を控える。未送信データを消去しない。 |
| 競合 | 自分の編集を退避して、最新DBを開き直し、差分を確認して必要な編集だけ反映する。古い全データで上書きしない。 |
| 通知が届かない | 端末の通知許可とグループのON状態を確認。テスト通知の結果とAPIログを確認する。通知の成功表示は端末表示を保証しない。 |
| 一覧・投稿のAPI障害 | デプロイ状態、APIのエラーログ、D1状態を確認。投稿の結果が不明なら同じ要求の再試行で確認する。 |
| 非公開データが共有に見える | 管理者がランキング共有を停止し、公開範囲とDB関数の適用状況を確認。修正後は匿名画面で再確認する。 |

## 戻すとき

フロントは直前の既知の正常コミットへコードを戻す。DBの成績を過去のバックアップへ自動で戻さない。通知APIは後方互換な直前バージョンを選び、request_id等の新しい列・テーブルを削除せず扱う。権限制御の修正を古い保存関数で上書きしない。DBの復元が必要なら新規入力の差分を保全し、復元対象・影響するグループ・公開範囲を確認して行う。

## 通知の扱い

現状のPushは補助的なお知らせであり、確実な配達やオフライン中の必達を保証しない。募集・チャットの本体を正とし、通知失敗は保存成功と区別する。永続送信キュー／自動再送や失敗アラートを運用要件にする場合は、その仕組みと試験を追加してから保証を案内する。
